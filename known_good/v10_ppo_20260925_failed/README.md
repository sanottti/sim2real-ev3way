# v10 — PPO(policy gradient)への切り替え実験 — 改善なし(2026-09-25)

> **【2026-09-29 注記】** このバージョンはN_HID=16のままでMPOS_SCALE=3.0
> (v9由来、内部一貫性あり)であり、v11以降で発覚したN_HID/MPOS_SCALE不一致
> バグの影響は受けていない。ただし比較対象のv7・v9評価の背景にある
> 「位置ドリフト」診断自体が実機ログ単位誤読に基づく可能性がある点は
> 他バージョンと同様(`SETUP_NOTES.md`訂正セクション参照)。

## 結論: 2回とも改善なし。v7が引き続きSim・実機ともに最良

CMA-ESからPPOへの最適化手法切り替え(ユーザー承認済み提案#4)を試したが、
**2回の試行(v9ベース・v7ベース)とも、warm start開始時点の重みを一歩も
上回れなかった**。保存された最終重みは、開始時点の重み(移行補正のみ適用)と
数値的に完全一致(誤差0.0000)。

## 実装

`ev3way_train_ppo.py`(新規)。app.c互換の決定的2層tanhネットワーク
(obs→tanh(W1)→hidden16→tanh(W2)→action)をActorとし、W2出力(tanh適用前)を
平均としたsquashed Gaussian policy(SAC同様のtanh補正付きlogp)を独自実装。
Criticは別ネットワーク。

## 試行1: v9からwarm start(失敗、原因判明・修正)

- iterations=2000, rollout_steps=6000, ent_coef=0.005で開始
- **バグ発覚**: rollout収集が完全ランダムシードのみを使い、`WORST_CASE_SEED`を
  ほぼ引かない設計だった。一方evaluate用の`EVAL_SEEDS`は6個中1個が必ず
  WORST_CASE_SEED。結果、訓練シグナルに複合最悪条件への頑健性維持が
  一切含まれず、iter100以降evalスコアがマイナス圏(-100前後)まで崩壊し
  続けた。iter525で中断
- 修正: `--worst-case-prob`(=1/6、EVAL_SEEDSと同じ構成比)を導入し
  rollout収集にもWORST_CASE_SEEDを混ぜるよう変更。`--ent-coef`も0.005→0.02に
  引き上げ

## 試行2: v7からwarm start(修正版、改善なし)

- **前提の訂正**: v9はEVAL_SEEDS(狭いサンプル)には強いが、100ランダムシードの
  広い統計比較ではv7に劣ると判明([[sim2real-ev3]]参照)。そのためv10は
  v9ではなくv7の重みからwarm startすべきと判断し、v7重みにMPOS_SCALE
  移行補正(10.0→3.0、誤差6e-8で検証済み)を適用して再スタート
- 修正版(worst_case_prob=1/6, ent_coef=0.02)で2000イテレーション完走
  (所要88.9分、クラッシュなし)。訓練中のeval scoreは開始直後-100付近まで
  落ち込んだ後、600→850台まで緩やかに回復する軌道を辿ったが、**warm start
  開始時点のbest_reward(1164.7)を一度も超えられなかった**
- 保存された最終重み(`ev3way_w1.npy`/`ev3way_w2.npy`)は、開始時点の
  v7(移行補正済み)と数値的に完全一致(row0最大差=0.0000, row2を逆補正した
  際の最大差=0.0000)。つまりPPOのbest tracking機構が「これまでのベストは
  常にwarm start地点のまま」と正しく判定し続けた結果であり、実装バグでは
  なく、単に一度も改善が見つからなかったという事実
- 100ランダムシード再評価(v7比較時と同一シード集合): 30秒完走95/100・
  5秒未満失敗5/100。v7単体の結果(94/100・5/100)とほぼ完全に一致(1点差は
  誤差範囲)。同一重みであることの独立確認にもなった

## わかったこと

- **best tracking機構(改善したときだけ重みを更新する設計)は正しく機能した**。
  改悪した重みを誤ってapp.cに反映するリスクは実際には発生しなかった
  (2回ともwarm start地点がそのまま保護された)
- v7の重みは、少なくともこの2回のPPO試行(それぞれ88〜90分規模)では
  改善の糸口が見つからないほど、この問題設定において「良い」局所解に
  居る可能性がある。あるいは、独自実装のPPO(rollout_steps=6000/iter、
  popsize相当が小さい、Critic・log_stdをゼロから学習)がこの規模の
  ネットワーク・この問題設定に対してまだ十分にチューニングされていない
  可能性もあり、この2回の結果だけでは「PPOはCMA-ESより劣る」と結論づける
  には材料不足
- CMA-ESが700〜2600世代規模(popsize×世代)の評価を要していたのに対し、
  PPOは2000 iteration×6000 stepsという、evaluate回数で見ると遥かに少ない
  データ量しか使っていない。フェアな比較のためには、同程度の総環境ステップ数
  (CMA-ESが実際に消費した数千万ステップ規模)をPPOにも与える必要がある

## 今後の選択肢(次に着手する場合)

1. rollout_steps・iterations をさらに増やし、CMA-ESに匹敵する総環境ステップ数を
   与えてPPOを再試行する(1回あたりの所要時間が大幅に伸びる)
2. Critic warm-up(policy更新を止めてvalue関数だけ先に学習させる期間を設ける)
   を追加し、学習初期の不正確なadvantage推定による破壊的な方策更新を防ぐ
3. 学習率(現在3e-4)やGAEのlambda等のハイパーパラメータを追加でチューニングする
4. PPO/policy gradientへの切り替えは一旦保留し、ユーザーが当初「次のステップの
   候補」として挙げていた#5(オモリ玉をランダムな位置にくっつけてロバスト性を
   高める、真の非対角慣性結合の導入)を先に試す
