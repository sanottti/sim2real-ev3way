# 教訓 — これまで踏んだバグと、同じ罠を避けるために

**このプロジェクトを引き継ぐ人が最初に読むべき文書です。**

このプロジェクトでは「計測そのものを誤らせるバグ」を何度も踏みました。
性能が出ない原因がアルゴリズムではなく計測・可視化・設定ズレだったケースが
大半です。以下を知らずに作業すると、同じ誤った結論を再生産します。

---

## 1. 実機ログの単位を3日間誤読していた(最大の事故)

**何が起きたか**: 実機CSVの `gyro_ang_x10` 列を「度×10」と思い込んで解析して
いたが、実際は**ラジアン×10**だった。記録値 `7` は `0.7°` ではなく
`0.7rad ≈ 40°`。

```c
// app.c 内。g_ang は rad(gyro_angle += g_spd * dt、g_spd は rad/s)
gyro_ang_x10 = (int16_t)(g_ang * 10.0f);
```

**何を誤らせたか**:
- 「傾きは常に0.7°以内に完璧制御されている」→ 実際は毎回40°まで傾いて**転倒**していた
- 「転倒ではなく操作者の手動停止」→ 実際は自動転倒(閾値45°)
- 「位置ドリフトが真の制約要因」という診断 → **存在しない問題**だった
- この誤診断に基づく v8〜v14 の報酬設計変更がすべて無駄になった

**教訓**: **ログの単位は変数名や思い込みで判断せず、必ずソースコードの
型・演算式まで遡って確認する。** `_x10` のような倍率サフィックスがあっても、
ベースの単位(度かラジアンか)はコード上の計算式で確定させること。

## 2. Sim と実機(app.c)の設定が知らぬ間にズレていた

`ev3way_train_run.py` と `nnapp/app.c` で以下が食い違っていた:

| 項目 | app.c (v7) | Sim | 影響 |
|---|---|---|---|
| 隠れ層 `N_HID` | 16 | 24 | **Simがapp.cの重みを読めない** |
| `MPOS_SCALE` | 10.0 | 3.0 | 位置ループゲインが3.33倍違う |

さらに移行検証スクリプトは `MPOS_SCALE=10.0` で「同一挙動」を確認していたのに、
実際の学習は `3.0` で走っていた(検証と学習のミスマッチ)。
**この結果 v11〜v14 の比較結果はすべて無効**。

**対策(導入済み)**: `test_sim_matches_appc.py` という回帰テストを作成。
app.c の `W1`/`W2` リテラルと正規化定数をパースし、Sim の `nn_forward()` と
出力が誤差 1e-5 未満で一致することを検証します。

```bash
python3 test_sim_matches_appc.py   # 作業開始時に必ず実行する
```

**教訓**: Sim と実機の二重管理が必要な定数は、**機械的に一致を検証する
仕組みを最初に作る**。人間のレビューでは必ず漏れます。

## 3. 物理パラメータを直すと、それに依存していた報酬の校正が壊れる

Sim のモータ最高速度を実機相当(115 rad/s → 17.8 rad/s)に修正した直後、
CMA-ES が19世代まったく改善しなくなりました。

原因は速度ペナルティ `0.02*(obs[4]²+obs[5]²)`(生の rad/s の二乗)。
これは `max_speed=115` 時代に暗黙に校正された係数で、当時は低速でも十分な
トルクが出たため滅多に発火しませんでした。`max_speed` を実機値にした結果、
**正しくバランスを取るのに必要な車輪速度(7〜10 rad/s)が最高速の40〜60%を
占めるようになり、このペナルティが正しい補正行動そのものを毎ステップ
-2〜-4.4 という支配的な大きさで罰していた**。

**対策**: 生の rad/s ではなく、その時点の `max_speed` に対する正規化値の
二乗に変更(スケール不変にした)。

**教訓**: 物理パラメータの変更は、**その値に暗黙に依存している報酬項・
閾値・コスト設定を芋づる式に壊す**。1項目変えたら、報酬の内訳を
1エピソード分トレースして確認すること。

## 4. カリキュラム中は「世代間のスコア比較」が全箇所で無効になる

カリキュラム学習(難易度を徐々に上げる)の最中、`best_flat` の更新を
`if cur_best > best_score:` という生スコアの大小比較で行っていました。

難易度が低い序盤ほど高スコアが出るため、**gen1 付近のたまたま易しい条件で
記録された個体が、以降どれだけ優れた個体が見つかっても永久に「最良」として
居座り続けていました**。best_reward の表示が最初の数世代から一切動かない
現象の正体がこれです。

**対策**: カリキュラム完了前は「これまでの最良」という概念自体が比較不能
なため、常に直近世代の最良個体を暫定採用する方式に変更。

**教訓**: カリキュラムを導入したら、**スコアを跨世代で比較している箇所を
全部洗い出す**(early-exit判定、best追跡、停滞検知…)。1箇所直しただけでは
別の箇所に同じバグが残ります(実際このプロジェクトでは2回踏みました)。

## 5. 可視化専用の実装は本体と別物として腐る

`record_population_video()`(学習結果の動画生成)は `EV3WayEnv` を使わず
独自のシミュレーションループを持っていたため、物理忠実化(8項目)を
一切反映していませんでした。結果、**実際は安定している重みが動画上では
1秒以内に全個体転倒して見える**という状態に。

この1つの関数に、独立した3つのバグがありました:
1. 忠実化フラグ(ジャイロ推定器・モータ速度等)が未反映
2. オモリ玉の固定位置が学習時のランダム化範囲を50〜62%超過
3. **物理タイムステップが制御周期5ms化に追従しておらず、起動デッドタイムが
   意図の2倍(0.30秒)実行されていた** ← 転倒の主因

**教訓**: 可視化や評価の「別実装」は、物理モデルを変更するたびに
**値だけでなくタイムステップの整合性まで**全数チェックする。
理想は共通の step 関数を全箇所で再利用すること。

## 6. Sim の生存時間だけで実機性能を判断してはいけない

v15 は Sim で v7 を大きく上回った(18.16s vs 11.16s)のに、**実機では逆に
悪化**(1.49s vs 2.27s)しました。

v15 は常にモータを全力で叩く bang-bang 制御を学習しており、実機のモータは
飽和時に逆起電力・電流制限で実トルクが出ないため裏目に出ました。

| | Sim飽和率 | 実機飽和率 | 実機生存 |
|---|---|---|---|
| v7 | 7.5% | 2.0% | **2.27s** |
| v15 | 38.2% | 41.1% | 1.49s |

**重要な副産物**: Sim は v15 の飽和率を正確に予測できていた(38.2% vs 41.1%)。
つまり物理忠実化は機能しており、**「Simが予測する制御の穏やかさ(飽和率)」は
実機性能の有用な予測指標**になります。

**教訓**: 採用判断は Sim の生存時間だけでなく、**制御スタイル(PWM飽和率・
|PWM|平均)が実機で成功したバージョンに似ているか**も見ること。

## 7. 実機バージョンの取り違え(運用事故)

「`app.c` のソースを更新した」ことと「実機に書き込まれている」ことは
**別の作業**です。ソースが v8→v9 と進む間、実機には数日前の v7 が
入ったままで、それに気づかず「v9の実機テスト結果」として記録・解析して
しまいました。

**対策(導入済み)**:
- `app.c` に `#define NN_VERSION "v16"` を持たせる
- ログファイル名に埋め込む(`nn_v16_000.csv`)
- CSVヘッダーにも書く(`# nn_weights_version=v16`)
- **起動時に LCD へ表示する**(`nnapp NN:v16`)← 人間が気づける唯一の砦

**教訓**: 実機テストの前に **必ず LCD 表示でバージョンを目視確認する**。

## 8. 長時間学習を落とさないための運用

2つの独立した問題があり、**両方の対策が必要**です:

| 問題 | 症状 | 対策 |
|---|---|---|
| CLIのバックグラウンドタスク管理 | 約30分で理由不明の kill | `nohup ... & disown`(PPID=1まで完全デタッチ) |
| macOS のスリープ | 夜間に何度もスリープし1世代が最大96分に悪化 | `caffeinate -ims` |

```bash
nohup caffeinate -ims python3 ev3way_train_run.py ... > train.log 2>&1 &
disown
# 確認
ps -o pid,ppid -p <PID>          # PPID=1 であること
pmset -g assertions | grep caffeinate
pmset -g batt                    # AC電源接続・Low Power Mode オフを確認
```

**Low Power Mode が ON だと計算が極端に遅くなります**(1世代が48倍に悪化した
実績あり)。`pmset -g | grep lowpowermode` が `0` であることを確認してください。

## 9. 評価スクリプトのバグで「0%〜100%」の謎の分散が出た

同じ重みが seed バッチによって 0/100 〜 100/100 と極端にばらつく問題が
長く未解決でしたが、原因は評価スクリプト側の `done` フラグ誤用でした。
`EV3WayEnv.step()` は**時間切れでも `done=True`** を返すため、
`not done` で成功判定すると「生き残って時間切れ」も失敗に数えてしまいます。

**教訓**: 終了フラグは「なぜ終わったか」を区別して扱う。
成功判定は転倒角度・位置超過を obs から直接判定すること
(`benchmark_100seed.py` は修正済み)。
